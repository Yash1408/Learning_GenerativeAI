# Document Chunking in RAG — Complete Practical Tutorial

> **From the basics to production design:** How to choose a chunking method based on document structure, handle embedding-model token limits, avoid losing context, and retrieve complete evidence.
>
> **Writing style:** Simple Indian English, with practical examples, diagrams, code, common mistakes, and questions to check your understanding.
>
> **Level:** Beginner → Intermediate → AI Engineer / Architect

## How to study this tutorial

Please don't try to remember all the names first. Understand the problem each technique solves. Follow this order:

1. What is a chunk and why do we need it?
2. How does document structure decide where to split?
3. What if a section is larger than the embedding model's token limit?
4. If we split again, how do we avoid losing meaning?
5. At search time, how do we bring back the required context?
6. How do we test whether our approach is actually working?

**One sentence to remember throughout:** We usually *embed small, meaningful chunks*, but sometimes we must *retrieve additional connected content* to answer correctly.

# Part 1 — Understand the basic concept

## 1. What is chunking in a RAG system?

Suppose you have a 150-page employee handbook. It covers leave policy, salary, insurance, travel expenses and resignation rules. A user asks: **“Can an employee take annual leave during probation?”**

It is not necessary to send all 150 pages to the LLM. We would like to find the small part which discusses probation and annual leave. To do this, we divide the document into smaller pieces called **chunks**.

A chunk is just a portion of extracted document content. It might contain a paragraph, a few sentences, a complete FAQ, one clause, a row group from a table, or a Python function.

### Indexing-time flow

![Indexing pipeline](images/01-indexing-overview.svg)

A simplified process:

1. **Read/parse the source:** Extract text, sections, tables and page information from the document.
2. **Split:** Make meaningful chunks, ideally respecting the document's structure.
3. **Check size:** Confirm that each final piece fits the embedding model's supported input limit.
4. **Create an embedding:** The model converts each chunk's text into a vector (a list of numbers representing its meaning).
5. **Store:** Put the vector in a searchable index, along with the original text and important metadata.

At question time, we embed the *question*, search similar stored vectors, and bring back the corresponding text for the LLM.

### A tiny example

Document:

```text
# Employee Handbook
## Leave Policy
Employees receive 20 annual leave days.
Employees on probation are not eligible for annual leave.
## Salary Policy
Salaries are credited on the last working day.
## Insurance Policy
Employees receive health insurance coverage.
```

Possible chunks:

```text
Chunk A — Leave Policy
Employees receive 20 annual leave days.
Employees on probation are not eligible for annual leave.

Chunk B — Salary Policy
Salaries are credited on the last working day.

Chunk C — Insurance Policy
Employees receive health insurance coverage.
```

The question about *probation leave* is much more likely to retrieve Chunk A than the salary or insurance chunks.

### What makes a good chunk?

A useful chunk generally has three qualities:

- **Relevant:** It deals with one topic, or one coherent subtopic.
- **Self-explanatory:** You can understand its meaning without guessing its heading, unit, subject or missing exception.
- **Within the input budget:** It fits the embedding model's actual token limit **including any heading/context added to it**.

These goals can conflict. That conflict is the central challenge in chunking.

> **Important:** Chunking happens during *indexing*. Recovering a parent section, neighbouring chunk or linked clause usually happens during *retrieval*. Both must work together.

---

## 2. File format is not the same as document structure

A common mistake is: “If file extension is PDF, use PDF chunking.” That is not enough.

A PDF can contain paragraphs, headings, tables, invoices, two-column pages, scanned images and footnotes. A DOCX can contain the same elements. Therefore, we should first understand what **content elements** exist inside the file.

![Improved content-first decision flow](images/02-content-first-decision.svg)

### What the diagram actually means

First inspect the content. Then select a **natural boundary** for splitting:

| What is inside the document? | Best first boundary | What information must remain connected? |
|---|---|---|
| Plain prose, article or blog | Paragraph → sentence | Nearby sentences explaining one idea |
| Technical manual / Markdown / HTML | Heading → subheading → paragraph | Parent heading, section path, definitions |
| FAQ | One complete question–answer pair | Question and its answer |
| Financial/operational table | Table → logical row group | Column headers, units, caption, row names |
| Legal agreement | Clause → subclause | Conditions, exceptions, defined terms, references |
| Python/Java code | Class → function/method → logical block | Function signature, enclosing class, relevant dependencies |
| Scanned or complex PDF | Recognised layout block | Reading order, page, position, field labels |
| Meeting transcript | Topic/turn/speaker block | Speaker, time and context around conversation |

**After deciding the structure, we still need a token-limit check.** A heading-based section may contain 3,000 tokens; a complete function may contain 2,000 tokens. Meaningful boundaries do not automatically guarantee the model can embed that text.

# Part 2 — Chunking methods in detail

## 3. Fixed-size chunking

This is the simplest approach. You tell the splitter to create a chunk with approximately a fixed number of characters or tokens.

Assume we have 1,000 tokens, choose a **300-token window**, and use **50-token overlap**.

```text
Chunk 1: tokens   1–300
Chunk 2: tokens 251–550   (50 tokens repeated)
Chunk 3: tokens 501–800   (50 tokens repeated)
Chunk 4: tokens 751–1000  (last chunk smaller)
```

### What is overlap?

Overlap means some information from the end of one chunk is also included at the beginning of the next chunk. It reduces the chance of losing the connection around the cut point.

### Problem with fixed-size splitting

Original sentence:

```text
Employees will be eligible for the bonus provided that they have
completed one full year of service.
```

A bad token window could divide it as:

```text
Chunk 1: Employees will be eligible for the bonus provided that they have
Chunk 2: completed one full year of service.
```

If the search retrieves only Chunk 1, the LLM may miss the important condition.

**When to use:** Quick baseline, clean uniform text, or a final emergency fallback after better boundaries have been attempted.

**When not to depend on it alone:** Legal agreements, code, tables, policies containing exceptions.

**Nuance:** “300 characters” and “300 tokens” are different. A token is not always a word. Some splitters count characters by default even when you name the parameter `chunk_size`.

---

## 4. Recursive chunking

Recursive chunking tries to preserve larger natural boundaries first, and only cuts smaller when needed.

Think of it as:

```text
Entire section
   │
   ├── Is it small enough? ── Yes → keep it
   │
   └── No → split by paragraph
                │
                ├── Paragraph fits? → keep it
                └── Still large → split by sentence
                                      │
                                      ├── Sentence fits? → keep it
                                      └── Too large → token-based fallback
```

Typical separator preference:

```python
separators = ["\n\n", "\n", ". ", " ", ""]
```

In practice, sentence splitting can use a proper sentence segmenter rather than a simple period delimiter, because abbreviations and decimal numbers contain periods too.

### Example

A report has three paragraphs of 180, 250 and 700 tokens. Suppose our desired target is 400 tokens.

- Paragraph 1 can be retained.
- Paragraph 2 can be retained or intelligently combined if the target allows it.
- Paragraph 3 is too large, so it is split further into sentences or smaller groups.

The advantage is that we are not blindly cutting exactly every 400 tokens.

### The important limitation

Recursive chunking *usually understands separators, not business meaning*. It may still separate a policy exception or a definition from the statement it qualifies. We will solve this later using metadata and retrieval expansion.

**Best suited for:** General reports, articles, extracted text, and oversized sections inside a structure-aware pipeline.

---

## 5. Sentence-based and paragraph-based chunking

These are easy to understand, but they have different risks.

### Sentence-based

Example:

```text
Sentence 1: Python is a programming language.
Sentence 2: Python supports object-oriented programming.
Sentence 3: Python is widely used in ML.
Sentence 4: The company provides 20 days of leave.
```

We may group Sentences 1–3 because they belong to one topic, and separate Sentence 4.

**Useful for:** Short factual material, transcripts and content without reliable headings.

**Risk:** A sentence such as “However, these rules do not apply to contractors” is not fully meaningful by itself. It refers to an earlier statement.

### Paragraph-based

Split by paragraph breaks (`\n\n`) because writers often keep related ideas in the same paragraph.

**Useful for:** Essays, articles, narratives and well-formatted documentation.

**Risk:** Some extracted PDFs have no reliable paragraph breaks; some paragraphs are extremely long. You must still enforce the token limit.

---

## 6. Heading-based / structure-aware chunking

This is particularly important for your Markdown tutorials, technical documents and policy manuals.

Take the following Markdown:

```markdown
# Machine Learning Guide

## Supervised Learning
Supervised learning uses labelled examples.

### Classification
Classification predicts categories.

### Regression
Regression predicts numeric values.

## Unsupervised Learning
Unsupervised learning uses unlabelled data.
```

Instead of splitting at random positions, preserve the heading structure:

```text
Child A:
Path = Machine Learning Guide > Supervised Learning > Classification
Content = Classification predicts categories.

Child B:
Path = Machine Learning Guide > Supervised Learning > Regression
Content = Regression predicts numeric values.

Child C:
Path = Machine Learning Guide > Unsupervised Learning
Content = Unsupervised learning uses unlabelled data.
```

### Why should we preserve heading paths?

Consider the text: “This model predicts categories.” Without the heading, we may not know whether it is discussing classification, tagging or something else. The heading adds useful context.

Possible metadata:

```json
{
  "document_id": "ml-guide-v1",
  "section_id": "supervised/classification",
  "heading_path": ["Machine Learning Guide", "Supervised Learning", "Classification"],
  "page": 5,
  "sequence_index": 8
}
```

**Nuance:** A heading can have many paragraphs. If the section is 2,500 tokens and our embedding model supports only 512, we do **not** blindly embed the entire section. We preserve it as a structural *parent* and split the body into smaller *children*.

## 7. Semantic chunking

Semantic means “based on meaning”. A semantic chunker tries to find where the topic changes, even if there is no heading.

Example:

```text
S1: Python is widely used in machine learning.
S2: Python has libraries for data processing.
S3: Python can be used to build APIs.
S4: Employees receive 20 annual leave days.
S5: Leave approval is required from a manager.
```

A reasonable outcome:

```text
Chunk A → S1, S2, S3  (Python-related topic)
Chunk B → S4, S5      (Leave policy topic)
```

### But how does it know meaning has changed?

One common implementation works like this:

![Semantic chunking process](images/08-semantic-process.svg)

1. Split the original document into **small, token-safe units**, often sentences or short sentence groups.
2. Generate embeddings of these small units.
3. Measure similarity between nearby units (often cosine similarity).
4. A large drop in neighbouring similarity may indicate a topic boundary.
5. Merge nearby similar units into meaningful groups.
6. **Validate the token size again**: one merged semantic group can still be too large for the embedding model.

### Very important question

**“If the document is 50,000 tokens, how does the semantic chunker embed it to decide boundaries?”**

It normally does **not** embed all 50,000 tokens in one request. It embeds the smaller units first, which must themselves fit the limit. The semantic grouping happens after that.

**Advantages:** Can find boundaries in unstructured text where headings are missing.

**Disadvantages:** Extra embedding work; similarity thresholds are heuristic; even semantically similar text might contain separate facts; topic shifts do not necessarily equal good retrieval boundaries.

**Best suited for:** Transcripts, meeting notes, long mixed-topic text and unstructured articles.

---

## 8. Parent-child (hierarchical) chunking

Parent-child is slightly different from ordinary splitting. It is not only a way to make chunks; it is also a **retrieval design**.

Assume the handbook's *Leave Policy* section has 2,000 tokens. Our model cannot embed it as one input. We split it into children:

```text
Parent: Leave Policy (2,000 tokens; stored as source text)
  ├── Child 1: Annual entitlement    (~350 tokens)
  ├── Child 2: Probation exceptions  (~350 tokens)
  ├── Child 3: Approval process      (~350 tokens)
  └── Child 4: Carry-forward rules   (~350 tokens)
  ... potentially more children
```

![Parent and child retrieval](images/06-parent-child.svg)

Each child stores `parent_id="leave-policy"`. We embed the children, not the whole oversized parent. The parent remains available in document storage.

When a query matches Child 2, we can fetch the complete relevant parent **or** a selected part of that parent to understand conditions and exceptions.

### Why not always retrieve the whole parent?

Because the generation LLM has its own context budget. If the parent is 40,000 tokens, retrieving everything is expensive and may distract the LLM. Prefer the closest subsection, surrounding children or the referenced clauses.

**Good for:** Long technical reports, research papers, legal and HR policy documents.

**Risk:** If parent expansion is too broad, retrieval precision goes down and token cost goes up.

---

## 9. Table-aware chunking

A table is not ordinary prose. Its meaning depends on the relationship between **row**, **column**, **unit**, **caption** and **value**.

Suppose the document contains:

| Year | Revenue (INR lakh) | Profit (INR lakh) |
|---|---:|---:|
| 2025 | 40 | 8 |
| 2026 | 55 | 12 |
| 2027 | 60 | 14 |
| 2028 | 70 | 17 |

A bad chunk might contain only:

```text
2026 55 12
```

The embedding/retrieval system cannot reliably know what `55` or `12` means. A good row-group chunk would instead look like:

```text
Table: Company Financial Performance
Units: INR lakh
Columns: Year | Revenue | Profit
Rows:
2026 | 55 | 12
2027 | 60 | 14
Source: annual-report, Table 4, page 18
```

![Table chunking example](images/07-table-aware.svg)

### What if a table contains 5,000 rows?

You should not embed all rows together. Instead:

1. Parse the table into a structured representation.
2. Create meaningful row groups (by year, department, category, or row ranges).
3. Repeat the table title, column headers and units in every child.
4. Store the original table and stable row identifiers separately.
5. Optionally add a *table-level summary* for retrieval.
6. For questions asking for **totals, sorting or exact arithmetic**, query the structured table or compute directly rather than relying only on vector embeddings.

**Common mistake:** Splitting a table into plain text every 400 tokens can separate numbers from their labels and produce wrong answers.

---

## 10. Legal contracts and policies: clause-aware chunking

Legal documents need special care because statements often contain exceptions, defined terms and references to other clauses.

Example:

```text
5.1 Employees with one year of service are eligible for the benefit.
5.2 Notwithstanding 5.1, employees serving notice are excluded.
5.3 "Employee" means a full-time confirmed staff member (see 2.1).
```

If the question is **“Is an employee serving notice eligible?”**, retrieving 5.1 alone can give the wrong answer. We also need Clause 5.2, and potentially the definition in 2.1.

Recommended design:

- Split at clause and subclause boundaries.
- Store clause ID, parent section, clause order and referenced clause IDs.
- Keep mandatory conditions/exceptions attached where possible.
- Resolve explicit `see 2.1`, `subject to 7.3`, or `notwithstanding 5.1` references at retrieval time.
- When a clause exceeds the token limit, split its logical parts into children, but preserve their clause ID and relevant links.

**Important:** Neighbouring-chunk retrieval is not enough if a definition appears 30 pages earlier. You need **cross-reference retrieval**.

---

## 11. Layout-aware chunking for PDFs, scans and forms

PDF is a container. A PDF page might display two columns, a table at the bottom and a footnote below it. Extracting its text in the wrong order can ruin the meaning before chunking even begins.

Example: An invoice has `Invoice Total` on the left and `₹18,750` on the right. A poor OCR/text extraction could list the value far away from its label.

A better process:

```text
PDF / scanned page
  → OCR if needed
  → detect reading order + headings + tables + key-value fields
  → produce structured blocks
  → chunk within each block using its appropriate strategy
  → preserve page / coordinates / table ID / field labels
```

**Example choices:** Paragraph block → recursive splitting; table block → table-aware; labelled field → keep label with value; heading section → structure-aware.

**When a page is scanned:** OCR accuracy and layout identification become prerequisites. Even a perfect splitter cannot repair every wrong OCR reading order.

---

## 12. Code-aware chunking

For source code, the right boundary is usually a complete function, method or class rather than a paragraph.

Example:

```python
class SalaryCalculator:
    def calculate_bonus(self, salary, years_of_service):
        if years_of_service < 1:
            return 0
        return salary * 0.10
```

If we index only `return salary * 0.10`, we have lost the eligibility condition and method name.

Prefer to use a parser or AST (Abstract Syntax Tree) to preserve logical code boundaries. Keep metadata such as file path, class, method, imports and code line numbers.

### What if one function itself has 3,000 tokens?

Then split it into smaller logical blocks (loop, branch, helper method, internal section), store the same function ID, and optionally repeat the signature and small relevant context. Use a token-safe fallback only when necessary.

**Nuance:** Just putting an import line in every chunk does not guarantee the code has all its dependencies. Search results may need to be expanded to related functions/classes.

# Part 3 — Embedding token limits: the question that changes the design

## 13. What exactly is the embedding token limit?

An embedding model accepts text input and converts it into a vector. Every model has its own maximum input length. A request above that limit might fail or be truncated, depending on the provider and configuration. **Never rely on silent truncation** because it may remove a critical exception.

For this tutorial, let's assume a **hypothetical maximum of 512 tokens**. This is for learning; it is not a claim about any specific provider.

A structure-aware splitter creates these sections:

| Section | Tokens | Can we embed directly? |
|---|---:|---|
| Introduction | 300 | Yes |
| Machine Learning Algorithms | 1,200 | No |
| Model Evaluation | 400 | Yes |

What should we do with the 1,200-token section?

![Oversized token limit fallback](images/03-token-budget-fallback.svg)

### Correct sequence

1. **Keep the original 1,200-token section** and its heading in parent storage.
2. Try to split by its **subheadings**.
3. For any oversized subsection, try **paragraphs**, then **sentences**.
4. Assemble bounded child chunks with a **target smaller than 512** (for example, 400 tokens).
5. If even one sentence / extracted field is too long, split using a **token-based fallback**.
6. Add the heading or context prefix to each child.
7. Count the tokens in the **final exact text sent for embedding**.
8. Embed only if the final text fits the actual model limit.

**Note:** With overlap, 1,200 tokens may produce **four** 400-token child chunks, not simply three. The actual count depends on overlap and boundary choices.

### Hard limit vs design target

| Term | Meaning |
|---|---|
| Model hard limit | Maximum supported embedding input, e.g. **512** in our hypothetical example |
| Chunk target | Your engineering choice, e.g. **400** tokens |
| Chunk overlap | Repeated context near neighbouring cuts, e.g. **40** tokens |
| Prefix budget | Tokens used by document title, heading, section path or contextual notes |
| Retrieval/LLM budget | Separate token allowance for evidence plus the prompt at question time |

**Why use a target below the hard limit?** Because the final embedding text may include headings and contextual prefixes, not only the chunk body. Leave some room and validate at the end.

## 14. What happens in each technique if a chunk is too large?

This is a very common interview question. The same model limit applies to every technique; the *preferred fallback* differs.

| Technique | Oversized chunk handling | What to preserve |
|---|---|---|
| Fixed-size | Reduce the token window below the model limit | Neighbour linkage and overlap |
| Recursive | Keep splitting at smaller separators, finally token windows | Paragraph/sentence order |
| Sentence-based | Group fewer sentences; split one huge sentence if necessary | Sentence relationship and source section |
| Paragraph-based | Split the large paragraph into sentences, then token windows | Paragraph ID, heading |
| Structure-aware | Split oversized section by subheading, paragraph, sentence | Heading path and parent ID |
| Semantic | Break large semantic group into smaller groups, then check limit | Topic label and sequence |
| Parent-child | Embed bounded children; store larger parent separately | `parent_id`, child order |
| Table-aware | Row groups with repeated headers/units | Row-column meaning and table ID |
| Layout-aware | Split within detected layout blocks | Page, reading order, field labels |
| Code-aware | Split large functions at logical blocks | Function/class identity and signature |

**Remember:** The token-limit problem is solved by **size control**. The context-loss problem is solved by **preserving relationships and recovering evidence**. They are related, but not the same problem.

---

## 15. Very important: token count is not word count or character count

Consider:

```text
I love machine learning.
```

A tokenizer does not necessarily produce one token per word. Some words can become multiple tokens; spaces and punctuation affect tokenisation. Token counts may differ across models.

When you write:

```python
RecursiveCharacterTextSplitter(chunk_size=400)
```

that generally means **400 characters by default**, not 400 model tokens. You must configure a model-compatible token counter if the requirement is a token budget.

Also note that if you add this prefix *after splitting*:

```text
Document: Employee Handbook
Section: Leave Policy > Probation
Content: ...
```

those prefix tokens also count. A 400-token body plus a 150-token prefix equals 550 tokens and would violate a hypothetical 512-token hard limit.

### Why not use the maximum token count all the time?

Even if a model can embed 8,000 tokens, a single chunk covering ML, payroll, legal and marketing may be less useful for targeted search than several topic-specific chunks. The vector describes the *whole input*, not a separate retrievable vector for each sentence.

It is a retrieval-quality trade-off, not only an API constraint.

# Part 4 — Why context can be lost even when all tokens fit

## 16. Context fragmentation: a realistic problem

Read the following policy **as one piece**:

> Employees are entitled to **20 annual leave days**. However, employees who are **serving probation are not eligible** for this leave benefit. The probation period is **six months** from the joining date.

Now imagine the section is long enough that the splitter makes two children:

```text
Child 1: Employees are entitled to 20 annual leave days.

Child 2: Employees serving probation are not eligible for annual leave.
         Probation lasts six months.
```

The user asks: **“How many annual leave days does a new employee get during probation?”**

The vector search may find Child 1 because it contains *annual leave days*. If the LLM receives Child 1 only, it could answer **“20 days”** and miss the exclusion.

![Context fragmentation](images/04-context-fragmentation.svg)

The embedding model was not necessarily wrong. The actual failure was **incomplete evidence retrieval**.

### Other ways context becomes fragmented

- **Exception separated from the rule:** “Eligible” is in one chunk; “except probation” is elsewhere.
- **Definition separated from the term:** A contract defines *Employee* earlier in the document.
- **Table headers separated:** “55” appears without *Revenue (INR lakh)*.
- **Reference separated:** Clause 5.1 says “subject to Clause 9.2”.
- **Code context separated:** A return statement appears without the eligibility check.
- **Heading removed:** The child says “this policy” without identifying which policy.

This is why **overlap alone is not a complete solution**.

# Part 5 — Five techniques for preserving and restoring context

## 17. Method 1 — Chunk overlap

Suppose we use a 400-token target with 50-token overlap. The last 50 tokens of one chunk become the first 50 tokens of the next one.

```text
Chunk 1  [ ----------- content A ----------- | overlap X ]
Chunk 2                                      [ overlap X | -------- content B -------- ]
```

If a conditional statement happens close to the boundary, overlap may keep its meaning together in at least one chunk.

**Where it works:** Nearby sentences, continuous paragraphs and text that crosses a cut boundary.

**Where it fails:** If a contract definition is 30 pages away, repeating 50 tokens will not bring that distant definition into the same chunk.

![Overlap is local](images/05-overlap-local-only.svg)

**Costs:** More embedded tokens, extra storage, duplicate retrieval and potentially noisy context.

> Starting with 10–15% overlap can be a reasonable experiment for prose. It is **not** a rule for every document. Some structure-based chunks need no overlap at all.

---

## 18. Method 2 — Parent-child retrieval

This is the technique I would particularly consider for long policy documents and technical manuals.

**Index time:**

1. Find a meaningful parent section, e.g. `Leave Policy`.
2. Store its full text separately.
3. Split it into smaller children, each within the embedding limit.
4. Embed the children.
5. Store `parent_id` in every child.

**Query time:**

1. Search child embeddings.
2. Suppose `Probation Rules` child matches.
3. Use its `parent_id` to locate the parent section.
4. Return the relevant parent/subsection, or related children, not necessarily the entire document.

Example metadata:

```json
{
  "document_id": "handbook-v2",
  "parent_id": "leave-policy",
  "chunk_id": "leave-policy-child-3",
  "sequence_index": 3,
  "heading_path": ["Employee Handbook", "Leave Policy", "Probation"]
}
```

### An important doubt: Doesn't the parent also exceed the token limit?

Yes, it may exceed the **embedding** model's limit. But we are **not embedding the full parent**. We store it as text. At question time, it is provided to a **different LLM for answering**, which has its own context window and budget.

If the parent is also too large for the answer-generation prompt, we fetch only the required subsection or nearby/referenced pieces.

**Trade-off:** Parent-child retrieval improves context completeness but can add irrelevant material if the parent is too broad.

---

## 19. Method 3 — Contextual chunking

A small chunk might not be clear on its own:

> “Employees are not eligible for these benefits during the probation period.”

The phrase *these benefits* is ambiguous.

A better embedding input includes a compact, faithful context:

```text
Document: Employee Handbook
Section: Annual Leave Policy
Topic: Probation eligibility

Employees are not eligible for these benefits during probation.
```

Now the embedding model has more information to associate the chunk with *annual leave*, *employee* and *probation*.

### Where does the context come from?

- **Deterministic metadata:** Existing document title, heading path, table caption.
- **Defined relationships:** Parent clause, section title, policy name.
- **Optional LLM-generated short context:** A verified explanation of how the text relates to the whole document.

**Caution 1:** If you generate context using an LLM, it can introduce incorrect details. Check that it is supported by the original source.

**Caution 2:** The contextual prefix counts towards the embedding input limit. If the limit is 512 and the prefix takes 90 tokens, we cannot send a 500-token body.

**Caution 3:** Some metadata can be stored for filtering without being inserted into the embedding text. Decide what should influence search versus what should only be available for reconstruction.

---

## 20. Method 4 — Neighbouring-chunk retrieval

Suppose the retriever finds `Chunk 5`, but the sentence just before it provides an important condition.

```text
Chunk 4    Chunk 5    Chunk 6
  ↑          ↑          ↑
previous    match      next
```

We can fetch the matching child plus one or two adjacent children, provided they belong to the same logical parent section.

Example metadata:

```json
{
  "chunk_id": 5,
  "parent_id": "leave-policy",
  "previous_chunk_id": 4,
  "next_chunk_id": 6
}
```

**Good for:** Continuous reports, transcripts, explanations spread across nearby paragraphs.

**Risk:** Adjacent chunks might contain unrelated topics, particularly near a section boundary. It is better to check `parent_id` and stop expansion at logical boundaries.

---

## 21. Method 5 — Cross-reference / linked-evidence retrieval

Consider a contract:

```text
Clause 5.1: A confirmed employee can claim the allowance.
Clause 5.2: Eligibility is subject to Clause 12.3.
...
Clause 12.3: Employees under notice are not eligible.
```

The user asks: **“Can an employee serving notice claim the allowance?”**

Fetching Clause 5.1 and its immediate neighbour might still miss Clause 12.3 if it appears far away. We should identify the explicit reference `12.3` and retrieve that clause as well.

Store relationships such as:

```json
{
  "chunk_id": "clause-5.2",
  "references": ["clause-12.3"]
}
```

Then retrieve the relevant linked clause when answering.

**Good for:** Legal documents, research papers with references, technical manuals with “see Section ...”, policies with definitions.

**Trade-off:** Requires reliable reference parsing and an extra retrieval step.

### Compare the five methods

| Method | Solves | Does **not** solve by itself |
|---|---|---|
| Overlap | Boundary-level loss | Distant references |
| Parent-child | Missing section-level context | A parent that is too huge or irrelevant |
| Contextual chunk | Missing heading/background meaning | Missing full exception in another section |
| Neighbour expansion | Nearby missing statements | Faraway dependencies |
| Cross-reference links | Explicit distant dependencies | References that are implicit or not detected |

These methods can be used **together**. For example, a legal RAG system might use clause-aware chunks + headings + parent IDs + referenced clause retrieval.

# Part 6 — How indexing and retrieval should fit together

## 22. Two different token budgets

![Two different token budgets](images/10-two-budgets.svg)

**Budget A: Embedding model's input.** At indexing time, every child chunk (including text prefix) must fit the embedding model's supported limit.

**Budget B: Answering LLM's context.** At question time, the question, instructions, retrieved passages, any tool outputs and space for the answer must fit the answering model's context budget.

This explains an apparent contradiction:

> “If I cannot embed a 2,000-token parent, how can I retrieve it later?”

Because **storing text is not the same as embedding it**. You can store a long parent externally, search its small indexed children, then fetch the necessary text at retrieval time. You only include as much parent context in the prompt as the answering LLM can reasonably use.

---

## 23. End-to-end production workflow

![Query-time context restoration](images/09-retrieval-restoration.svg)

### During ingestion

1. Detect format and parse content correctly (OCR/layout extraction if needed).
2. Identify content elements: heading, paragraph, table, clause, code block.
3. Select appropriate structural boundaries.
4. Save parent sections / source objects with stable IDs.
5. Split oversized units using token-aware recursive fallback.
6. Add small, faithful contextual information where useful.
7. Validate final exact embedding input against the model's actual limit.
8. Embed children and store vectors with metadata and links.

### When a user asks a question

1. Convert the user question to a query representation/embedding.
2. Search for likely matching child chunks (vector search or hybrid keyword + vector search).
3. Optionally rerank the best candidates using their actual text.
4. Identify whether required rules, exceptions, definitions, tables or references are missing.
5. Fetch relevant parent sections, neighbouring chunks or cross-referenced clauses.
6. Deduplicate repeated overlap and remove unrelated text.
7. Enforce the answering LLM's prompt budget.
8. Ask the LLM to answer **only from supported evidence**, ideally with source citations.

### Why hybrid search can help

Vector similarity is useful for meaning, but precise terms like *Clause 12.3*, *invoice ID*, *method name* or *product code* may be better served by keyword or structured filters. Hybrid retrieval combines these approaches.

### Why reranking can help

The first vector search gives *candidates*. A reranker examines the query and candidate text more directly to sort them by relevance. It does not, by itself, reconstruct missing exceptions; the expansion step still matters.

# Part 7 — Implementation with Python

## 24. A token-safe structure-aware implementation

The following example is runnable locally. It demonstrates **Markdown headers → recursive splitting → final token validation**. It intentionally does not call any paid embedding API. That makes it easier to understand the chunking logic first.

**Install:**

```bash
python -m pip install langchain-text-splitters tiktoken
```

**Run:**

```bash
python examples/structure_aware_chunking.py
```

The script is included in `examples/structure_aware_chunking.py`. Here is the complete version:

```python
from langchain_text_splitters import (
    MarkdownHeaderTextSplitter,
    RecursiveCharacterTextSplitter,
)
import tiktoken

# Educational tokenizer. In production, use the tokenizer/counting rules
# that match your actual embedding model and endpoint.
encoder = tiktoken.get_encoding("cl100k_base")

MODEL_LIMIT = 512           # HYPOTHETICAL model limit
TARGET_TOTAL = 400          # Our design target, including metadata prefix
OVERLAP = 40


def count_tokens(text: str) -> int:
    return len(encoder.encode(text))


def make_prefix(metadata: dict) -> str:
    heading_path = " > ".join(str(v) for v in metadata.values())
    return f"Document: Employee Handbook\nSection: {heading_path}\n"


markdown = """
# Employee Handbook

## Leave Policy
Employees receive 20 annual leave days. Employees under probation are
not eligible for annual leave. Probation lasts six months.

## Salary Policy
Salary is credited on the last working day of each month.
"""

# Step 1: Split by headings. The splitter retains heading values in metadata.
header_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "document"), ("##", "section")],
)
sections = header_splitter.split_text(markdown)

final_chunks = []
for section_index, section in enumerate(sections):
    prefix = make_prefix(section.metadata)

    # Step 2: Reserve room for the prefix BEFORE splitting the body.
    available_body = TARGET_TOTAL - count_tokens(prefix)
    if available_body <= OVERLAP:
        raise ValueError("Prefix consumes too many tokens for this target")

    # Step 3: Split large section bodies using token-aware length counting.
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=available_body,
        chunk_overlap=OVERLAP,
        length_function=count_tokens,
        separators=["\n\n", "\n", ". ", " ", ""],
    )
    children = splitter.split_text(section.page_content)

    for child_index, child in enumerate(children):
        exact_input = prefix + child
        measured = count_tokens(exact_input)

        # Step 4: Validate the exact embedding input, after adding the prefix.
        if measured > MODEL_LIMIT or measured > TARGET_TOTAL:
            raise ValueError(f"Oversized chunk: {measured} tokens")

        final_chunks.append({
            "chunk_id": f"section-{section_index}-child-{child_index}",
            "parent_id": f"section-{section_index}",
            "text_to_embed": exact_input,
            "tokens": measured,
            "metadata": section.metadata,
        })

for chunk in final_chunks:
    print("\n", chunk["chunk_id"], "-", chunk["tokens"], "tokens")
    print(chunk["text_to_embed"])
```

### Understand the code line by line

- `MarkdownHeaderTextSplitter` separates **logical sections**, not arbitrary 400-character blocks.
- `make_prefix` adds the document and heading path so a small child has enough background to be understood.
- `count_tokens(prefix)` reserves room before splitting the body.
- `length_function=count_tokens` tells the recursive splitter to measure token count, not only characters.
- `parent_id` keeps a link to the original logical section.
- The final `if measured > MODEL_LIMIT` is a **hard safety check** before embedding.

**Important production note:** This demonstration uses a general-purpose tokenizer, not a guarantee that the count matches your actual embedding service. Verify tokenizer compatibility and API limits, including any batch limits. Some text splitters can also return imperfect boundaries in edge cases; an exact final check is compulsory. If a final chunk fails, split it again rather than silently truncating it.

### What does this script not do?

It does not create a vector database, embed using Azure/OpenAI, implement parent storage, resolve cross-references, or use rerankers. Those are separate responsibilities and should be added only after the chunk boundaries are working correctly.

## 25. Very simple Python: see overlapping token windows

If you want to understand the underlying idea without LangChain, the following code creates overlapping token windows. This is a **fallback example**, not a document-aware parser.

```python
import tiktoken

encoder = tiktoken.get_encoding("cl100k_base")


def token_windows(text, size=100, overlap=20):
    assert 0 <= overlap < size
    tokens = encoder.encode(text)
    step = size - overlap
    chunks = []

    for start in range(0, len(tokens), step):
        piece = tokens[start:start + size]
        if not piece:
            break
        chunk_text = encoder.decode(piece)
        chunks.append(chunk_text)
        if start + size >= len(tokens):
            break
    return chunks

text = "Machine learning is useful. " * 100
for i, part in enumerate(token_windows(text), start=1):
    print(i, len(encoder.encode(part)), repr(part[:60]))
```

**Technical nuance:** Decoding arbitrary token windows can cause imperfect byte/Unicode boundaries for some tokenizers. For robust systems, prefer token-aware text splitting that preserves valid character spans, and always re-tokenize the final exact text before embedding.

# Part 8 — Choosing a good chunk size

## 27. Which chunk size should you use?

There is no universal best number. For text-heavy RAG systems, experimenting with a few hundred tokens per chunk can be a good starting point, but the correct choice depends on the content and questions.

| Document | Initial experiment | Extra information to retain |
|---|---|---|
| Articles / prose | 300–500 tokens | Paragraph boundaries, maybe some overlap |
| Technical manuals | 400–800 tokens | Heading path, subsection ID |
| HR policies | Clause / section-based, token-capped | Exceptions, parent section, definitions |
| Legal contracts | Clause-based, token-capped | Clause ID and cross-references |
| FAQs | Entire Q&A pair | Question + answer together |
| Tables | Logical row group | Header, units, caption, row IDs |
| Code | Function/method when possible | Signature, class, imports, path |
| Research papers | Section → bounded children | Parent, page, citations and figure references |

These are **experimentation ranges**, not model limits or guaranteed recommendations. Always adjust them to your actual embedding model's supported token count.

### What if chunks are too small?

A child may say “This is not applicable” without naming the policy. Retrieval becomes ambiguous; related sentences are fragmented; the system may need many chunks to reconstruct one answer.

### What if chunks are too large?

A chunk may mix unrelated topics. A single embedding becomes less targeted; retrieval includes extra content, and prompt cost may increase. Even within the model limit, bigger is not always better.

### Should overlap always be 20%?

No. Overlap is useful when content naturally flows between chunks. For independent FAQ answers, well-formed clauses or row groups, repeating everything may be unnecessary. Try a small amount and evaluate the actual impact.

---

## 28. How to evaluate the chunking strategy

Do not decide based only on how beautiful the chunks look. Test the full **question → retrieval → answer** flow.

Create 30–100 representative questions with correct evidence locations. Include simple questions and difficult ones:

1. One sentence directly answers the question.
2. The answer requires a condition and an exception.
3. The definition exists in a different section.
4. The answer comes from a table row with units.
5. The answer refers to a clause on another page.
6. Multiple passages appear relevant, but only one is correct.

### Important evaluation terms

**Recall@k:** Out of the necessary relevant evidence items, how many did our top-k retrieval results recover?

**Precision@k:** Out of the k retrieved items, how many were genuinely relevant?

**Evidence completeness:** Did we retrieve *all necessary conditions, exceptions, definitions and row labels* to answer correctly?

**Answer correctness:** Did the LLM give the correct response using the retrieved evidence?

**Citation accuracy:** Does the cited source actually support the statement?

**Latency and cost:** How much extra work is caused by embeddings, overlap, reranking and parent expansion?

### Example evaluation

Question: “How many leave days does an employee get during probation?”

- Retriever returns the “20 days” sentence only → **Incomplete evidence**, likely wrong answer.
- Retriever returns both the general entitlement and probation exception → **Complete evidence**, can answer correctly.
- Retriever returns the entire 150-page handbook → Maybe complete, but too expensive and unfocused.

The best approach gives **complete and focused evidence**, not simply the largest number of retrieved tokens.

# Part 9 — Common mistakes and interview questions

## 29. Ten common mistakes

1. **Assuming every PDF needs the same splitter.** A PDF may contain several different content types.
2. **Confusing `chunk_size` characters with tokens.** Check the length function.
3. **Splitting at the hard model limit.** Heading/context prefixes may push inputs over the limit.
4. **Ignoring a large logical unit.** Even one heading section or function can be oversized.
5. **Using overlap as a complete context solution.** It only protects local boundaries.
6. **Dropping heading/page/parent metadata.** This makes retrieval reconstruction difficult.
7. **Separating table values from headers.** The result may become meaningless.
8. **Embedding entire massive semantic groups.** Semantic grouping still needs final token checks.
9. **Always retrieving full parents.** This can add noise and exceed generation budgets.
10. **Testing only retrieval similarity.** Evaluate complete evidence and final answer quality.

---

## 30. Architecture questions with explanation

### Q1. Why don't we simply embed the complete document?

Because a document may exceed the embedding limit, and even if it fits, one vector for many unrelated topics is often less useful for targeted retrieval. Chunking creates more precise search units.

### Q2. If our model supports 8,000 tokens, should every chunk contain 8,000 tokens?

No. **8,000 is a maximum input constraint, not necessarily the best retrieval granularity.** Experiment with smaller topic-focused chunks.

### Q3. Can a structure-aware chunk be larger than the embedding limit?

Yes. Heading boundaries preserve meaning but do not guarantee size. Split the oversized section further and store its parent relationship.

### Q4. What happens if a semantic chunk is too large?

Split the semantic group again using meaningful sentence boundaries or recursive token-safe splitting, while retaining topic metadata. Verify the final exact token count.

### Q5. Does chunk overlap guarantee no context loss?

No. It helps near a boundary, not across distant pages or references.

### Q6. Why do we use parent-child retrieval?

Children are small and precise for vector search; the parent (or related sections) provides context for accurate interpretation.

### Q7. Can a parent exceed the embedding model's maximum tokens?

Yes, **if it is stored rather than embedded as one input**. The returned parent/subsection must still fit the answering LLM's prompt budget.

### Q8. Why do we need metadata if we already have embeddings?

Embeddings help locate likely related text. Metadata lets us know its heading, page, parent, order and linked evidence. These are needed for reconstructing the correct context and providing citations.

### Q9. How is token-aware splitting different from context preservation?

Token-aware splitting solves an **API/input constraint**. Context preservation solves a **meaning/evidence completeness problem**. Both are necessary.

### Q10. Which chunking strategy is best for production RAG?

There is no single best strategy. A strong starting design is **content-aware splitting → token-safe fallback → linked metadata → selective context restoration**. Use evaluation to decide where semantic, table-aware, clause-aware or AST-aware processing adds value.

# Part 11 — Practical decision checklist

Before you implement a production chunking pipeline, check:

- [ ] Did I inspect real document elements rather than choosing by file extension only?
- [ ] Are headings, tables, clauses and code functions split at suitable boundaries?
- [ ] Did I choose the tokenizer/counting rules compatible with the embedding model?
- [ ] Is the **exact final embedding input** validated after adding headings/context?
- [ ] Do I have a safe fallback for oversized sentences, functions and semantic groups?
- [ ] Do the chunks retain stable document, parent, section and sequence IDs?
- [ ] Are table headers/units and legal definitions/references preserved?
- [ ] Have I planned how to retrieve parents, neighbours and linked evidence?
- [ ] Am I controlling the answering LLM's separate prompt budget?
- [ ] Did I evaluate answer correctness and **evidence completeness**, not only similarity?

## Final mental model

Think of the design as three separate jobs:

| Job | Question | Typical technique |
|---|---|---|
| **Understand structure** | Where is it sensible to split? | Heading, paragraph, semantic, table, clause or AST boundaries |
| **Respect the model** | Does each input fit the embedding limit? | Token-aware fallback + final validation |
| **Restore full meaning** | Did the query retrieve everything needed to answer? | Parent-child, contextual prefixes, neighbours, cross-references, reranking |

> **Don't design the system only to make every chunk 400 tokens. Design it so each indexed chunk is meaningful, each model call is valid, and every answer is supported by complete evidence.**
